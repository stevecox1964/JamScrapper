## TL;DR

The "AI Video" synthetic music-video compositor is built, working, committed, and pushed to `main` (commit `ed2a614`). It composes a slideshow music video from already-fetched images when a track has no real YouTube video, or on demand via a header toggle. The next session's highest-value step is the **backend image-pool expansion** (iTunes/Deezer/Cover Art Archive → 15–40 images per track) so the slideshow has more variety than the current ~3–5 images.

## What was done this session

- Built `frontend/src/components/SyntheticVideo.jsx` — a Canvas 2D compositor that turns a track's still images into a music video. Final motion model (user-approved through several iterations): each image **scrolls in from the right → holds centered (~3.5s) → scrolls off left** as the next slides in, over a blurred crossfading background with vignette + constant film grain. No beat reaction (user explicitly removed the earlier pulsing/Ken-Burns version).
- Added the **AI Video** header toggle in `App.jsx` — forces the compositor on even when a real YouTube video exists, for A/B comparison. Button flips to "Real Video" (purple/pink glow). Real video keeps playing underneath the opaque compositor, so toggling back is instant.
- Wired the compositor's trigger: `appMode === 'live' && (youtubeSearchStatus === 'not_found' || forceSynthetic)`. Banner text adapts ("AI Video Mode" when forced vs "Image-Only Mode" when genuinely no video).
- Updated `README.md`: new "AI Video — Synthetic Music Videos" section, project-structure entries, usage step, roadmap item.
- Also committed the pre-existing uncommitted synthetic-fallback work that was in the tree (miss-cache in `db.py`, `YtMissesPanel.jsx`, `YouTubeBackground.jsx` unplayable-error flip, `TrackInfo.jsx`) — all part of the same feature.
- Committed as `ed2a614` and pushed to `origin/main`.

## Debugging journey (so it isn't repeated)

The compositor showed a black screen at first. Three stacked bugs, all fixed:
1. **Layer collision** — canvas was `z-index: 0`, tied with the YouTube iframe; iframe won. Fixed to `z-index: 1` (above raw video layer 0, below visualizer 2).
2. **Cross-origin image rejection** — original version reused `MediaTextureManager`, which sets `crossOrigin="anonymous"` (needed for 3D WebGL textures); remote photos without CORS headers failed to load. The compositor now loads its **own** images with no crossOrigin (2D draw never reads pixels back, so a tainted canvas is harmless).
3. **Relative URL 404** — `media.youtubeThumbnailUrl` is backend-relative (`/media/thumbnails/...`) and 404s on the Vite port (5173). Added `resolveUrl()` prefixing relative URLs with `API_BASE` (`http://localhost:8766` in dev), matching the `SongHistory.jsx` convention.

## Decisions locked in this session

- **Compositor first, AI generation (FAL) later** — user chose the real-image compositor over FAL img2video generation. The `fal-video-pipeline` skill exists for a future "regen" phase, but this phase is real-time, free, no per-track cost. (See `memory/synthetic_video_plan.md`.)
- **Motion = scroll-in / hold / scroll-out slideshow, no beat reaction** — user explicitly rejected the pulsing/zoom/Ken-Burns version. Keep it calm and constant.
- **Compositor loads its own images (not via MediaTextureManager)** — to bypass the CORS requirement. Don't refactor it back onto the shared manager.
- **Tune knobs:** `HOLD_SECONDS = 3.5`, `TRANSITION_SECONDS = 1.8` in `SyntheticVideo.jsx`. User is happy with current values.

## Open questions

- Whether to expand the image pool now (backend) vs. add the FAL "regen" path — user leaned toward "Compositor now, AI later" framing but explicitly picked compositor for this phase. Pool expansion is the agreed next enhancement but not yet greenlit to start.

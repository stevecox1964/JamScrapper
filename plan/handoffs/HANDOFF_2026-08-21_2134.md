## TL;DR

Rando now records every finish and skip to a new `rando_stats` table and weights future picks
from it — the learning loop is live and collecting. Player mode no longer dies on embed-blocked
videos; it falls back to the local file. All UI complaints from this session are fixed.

## What was done this session

Continues directly from the 2033 handoff (Rando + full-volume fix), same day.

### 1. Rando learns — the main work

- New `rando_stats` table in `backend/db.py`: `video_id`, `artist`, `title`, `picks`,
  `finishes`, `skips`, `played_seconds`, `last_played_at`.
- `radio.py` gained `_record()` (additive upsert), `_taste()` (per-song multiplier),
  `finished()`, and `skip()`.
- **Skip is the only explicit negative.** Strength scales by how early the skip came;
  `SKIP_GRACE = 45s`, past which a skip counts for nothing. It subtracts from the session mood
  counter, so the penalty decays — a skip is a mood, not a ban.
- **Finishing a song is the only positive signal.** No thumbs-up button, deliberately.
- Both directions saturate at `TASTE_CAP = 3`, giving a per-song multiplier of 0.4x–1.6x.
- New routes: `POST /radio/finished`, `POST /radio/skip` (both in `server.py`).
- `App.jsx` `reportRadio()` sends both. `handleTrackEnded` reports a finish, `handleNext`
  reports a skip.
- Verified by simulating 400 plays of a listener who always skipped metal and always finished
  new wave: new wave rose to 1.13x average, heavy metal fell to 0.88x, per-song range
  0.60x–1.60x. **The 333 rows of simulated data were then deleted** — `rando_stats` is empty
  and `play_history` / `tracks` were never touched.

### 2. Freshness signal — a wrong first attempt, then fixed

- First built novelty on **play counts**. Checking the real DB killed it: 682 history rows for
  681 distinct songs, so 680 songs have exactly one play. Counts carry no information here.
- Rewrote as **recency** (`_last_played()`), spanning 2026-02-27 to today. Measured effect:
  68% of the library is 60+ days stale, but 76% of picks are — a real, modest lean.
- `rando_stats.last_played_at` also feeds recency, so Rando's own plays make songs stale. This
  closes the gap that was logged in the backlog earlier the same session.

### 3. Player mode died on unplayable videos — user-reported bug

- Root cause: live mode had an `onError` handler, **player mode had none**. An embed-blocked
  video left the player on a dead frame forever, and with Rando on it hung permanently. The
  reported symptom was "I still have to copy the URL to the song".
- Added `onError` to the player-mode YT player, wired to `handlePlayerVideoError`.
- **Falls back to the local file** (`LocalVideoPlayer.jsx`, new) before giving up — 389 mp4s are
  on disk and `server.py:1109` already serves them with range support.
- Only purges from the library via `/yt-unplayable` if YouTube reported a *permanent* code
  (100 / 101 / 150). A transient error no longer costs a track.
- **A dead video never records a skip** — that would teach Rando to avoid a song never heard.
- Five consecutive failures stop the player rather than spinning.

### 4. UI fixes

- Rando button label is now always **"Rando"**. The first attempt only changed the on-state;
  the whole button was meant to be renamed.
- **Copy link in player mode.** `TrackInfo.jsx` already had a share link and Copy button, gated
  on `media.youtubeVideoId` — and `App.jsx` built player-mode `displayMedia` without that field,
  so the row silently vanished. One-line fix. A duplicate Copy button was briefly added to
  `PlayerControls.jsx` and then removed; it belongs on the slide-out card only.
- **Player bar / track card collision.** The card is `bottom: 24px; left: 0`, up to ~530px wide;
  the bar was centred at 920px with a higher z-index, so it covered the card. The bar is now
  right-aligned at `width: min(920px, calc(100vw - 570px))`, with a `max-width: 1180px` media
  query that stacks it above the card on narrow screens.
- **Font sizes** in the player bar raised to the 12px floor (several were 9–10px): title 12→15,
  artist 10→13, buttons 10→13, time and volume 10→12, queue position 9→12, up-next 9/11→12/13.
  Greys lightened — several were dark grey on black.

## Decisions locked in this session

- **No thumbs-up button, ever.** Reasoning: "eventually, everything is an up arrow" — an
  explicit positive saturates and dies. Finishing a song is the positive signal.
- **A skip is a mood, not a ban.** Penalties must always decay.
- **Recency, not play counts,** is the freshness signal in this data. Do not reintroduce counts.
- **Copy link lives on the slide-out card**, not in the player bar.
- **The visualizer and FFT code stays.** Kept on purpose in case Steve returns to it; the
  natural moment to revisit is when the Pandora drain ends and the audio capture dies with it.
  Written up in `plan/BACKLOG.md`. Do not remove it as a side effect of another task.
- **The library is being built deliberately.** Steve is draining Pandora for a few more months,
  then will run this app standalone. The 624-song pool is a work in progress by design — do not
  describe it as the "wrong" pool.

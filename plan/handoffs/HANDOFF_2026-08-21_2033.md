## TL;DR

Two features landed this session, both built and building clean, neither tested by the user yet:
a fix for songs playing quiet after the first track, and a new **Radio** button that picks songs
with a genre-drift random walk. Next session should start by asking the user how Radio *felt*

## What was done this session

**1. Full-volume playback fix**
- Root cause: the end-of-track fade in `frontend/src/components/YouTubeBackground.jsx` called
  `p.setVolume(0)` and never restored it. `loadVideoById` keeps the player's volume, so every
  song after the first started quiet and got quieter.
- Added `userVolumeRef` (defaults to `1`) and a module-level `applyVolume(player, volume)` helper
  that calls `unMute()` + `setVolume()`.
- Volume is now re-applied on: player creation (`onReady`), `loadVideoById`, resume-same-video,
  and from the poll loop whenever the player is outside the fade window and drifted from target.
- `onPlayerState` and `getState` now report `userVolumeRef.current` instead of the live (possibly
  faded) `getVolume()`, so the fade no longer leaks into the UI slider or into persisted state.
- `frontend/src/App.jsx`: stopped restoring `state.volume` from `GET /player-state` on mount.
  Playback always starts at full. The slider still works within a session.
- Live-mode player at `YouTubeBackground.jsx:164` was deliberately left muted — that is correct.

**2. Radio — genre-drift random song picker**
- New `backend/radio.py` with `RadioDJ`. Weighted random pick over all playable `tracks` rows.
- Genre source: `play_history.genres` per song, falling back to `artists.genres` per artist slug.
  `_slugify()` mirrors `ArtistStore.slugify` exactly (verified against non-ASCII names).
- Keeps an in-memory `Counter` "mood". Each pick decays it by `MOOD_DECAY` then folds in the
  picked song's genres — this is the drift back "in".
- `WILDCARD_CHANCE = 0.18` ignores genre entirely on a pick — this is the "out".
- `deque` of the last `RECENT_MEMORY = 40` video ids prevents repeats; if everything is stale it
  forgets the oldest half rather than returning nothing.
- `backend/server.py`: added `GET /radio/next?artist=&title=` and `GET /radio/reset`; added
  `from urllib.parse import parse_qs, urlparse`; instantiated `radio_dj = RadioDJ(_http_db_conn)`
  alongside the other HTTP-thread stores.
- `frontend/src/App.jsx`: **Radio** header toggle, `appendRadioTrack()`, `toggleRadio()`,
  `handleTrackEnded()`. Radio appends to the queue and advances; it never replaces the queue.
- `onTrackEnded` and the PlayerControls `onNext` both route through `handleTrackEnded`, so while
  Radio is on, **Next** gives a fresh pick instead of wrapping the queue.

**Verification performed**
- Ran `RadioDJ` against the real `backend/data/visualaudio.db`: 624 playable tracks, 601 with
  genres, 682 history rows, 225 artist profiles. 12 sequential picks seeded from Radiohead
  produced a coherent rock/alt-rock run with one wildcard (Eurythmics) — the intended behaviour.
- `npx vite build` passes for both changes (only the pre-existing >500 kB chunk warning).
- `ast.parse` clean on `server.py` and `radio.py`.

## Decisions locked in this session

- **Playback always starts at full volume.** Saved volume is no longer restored on mount — the
  user's ask was "always full volume", and the old saved values were polluted by the fade bug.
- **Genre drift walk over plain shuffle.** User chose it explicitly; plain shuffle jumps from
  metal to synth-pop with no logic.
- **Radio is endless, not one-shot.** User chose it explicitly; the drift only gets interesting
  over several songs.
- **Radio mood state is per-server-process, not persisted.** Restarting the backend resets the
  walk. Simplest thing that works; revisit only if the user asks.
- **Radio appends to the queue rather than replacing it**, so an existing playlist is not lost.

## Open questions

- **Do the tuning knobs feel right?** The user has not heard it yet. The three that matter, all
  at the top of `backend/radio.py`: `WILDCARD_CHANCE = 0.18` (raise = wander more),
  `MOOD_DECAY = 0.75` (raise = stay in a genre longer), `SHARPNESS = 2.0` (raise = match harder).
- **Should the 23 tracks with no genre tags be handled differently?** Right now `BASELINE_WEIGHT`
  gives them a small constant chance, so they surface as pseudo-wildcards.
- **Should the queue be capped?** Radio grows `playerQueue` without bound and the whole queue is
  POSTed to `/player-state` every 2 s. Fine for a session; a long unattended run will bloat it.
